# CLAUDE.md

Guidance for working in this repo. Read alongside `README.md` (user-facing) — this file is the build/architecture contract.

## What this is

A browser-based parametric builder for 3D-printable storage, with a live 3D preview and print-ready **STL** / **3MF** export. Five **object types** (see "Object types" below):

- **Bin** — a Gridfinity-style bin. Gridfinity-aware (42mm grid, chamfered foot, stacking lip) but not constrained by it: the grid pitch is adjustable and a custom-size mode frees the footprint entirely.
- **Box** — a closed box with a choice of **top type**: a **sliding lid** or a print-in-place **hinged lid**.
- **Skadis** — a container/holder that clips onto an IKEA SKÅDIS pegboard via print-in-place back hooks. Rectangular (adjustable corner radius; 0 = sharp) or round/elliptical cross-section, a full-height taper, an open-bottom rim shelf, and a degrees-based opening on the front or either side.
- **Litho** — a lithophane: an uploaded photo embossed as varying thickness in a panel that reveals the picture when backlit. Rectangular (corner radius) or round (with a bottom stand flat), optional hanging hole. STL/3MF only — no STEP.
- **Fan** — a lithophane hand fan: N blades pivoting on a common hub, with one uploaded photo spanning the whole **open** fan (each blade carries the slice that lands under it). Parametric blade silhouette, a flat untextured pivot zone, a rivet hole, and image zoom/offset to frame the picture on the fan. STL/3MF only — no STEP.

Runs 100% in-browser. No backend. Designs persist in localStorage (autosave + named saves) and can be shared via URL.

## Stack

React 18 + Vite 5 + TypeScript (strict) + Three.js. CSG via `manifold-3d` (WASM; guarantees watertight/manifold boolean output). Those four are the only runtime deps — keep it that way unless there's a strong reason.

## Commands

```bash
npm install
npm run dev      # vite dev server (http://localhost:5173 by default)
npm run build    # tsc-less vite production build to dist/
npm run preview  # serve the production build
```

There is **no test suite and no linter configured**. "Verify" means: `npm run build` compiles clean, then load the app and check the 3D preview + export in a browser. Don't claim something works without doing that.

`npm run build` (Vite/esbuild) does **not** full-type-check. Run `npx tsc --noEmit` for that — but note **two known pre-existing errors** it reports (the `manifold-3d/manifold.wasm?url` import has no type decl; a `Uint8Array`→`BlobPart` cast in the ZIP writer). Both are harmless and don't affect the Vite build; ignore them and only act on *new* errors.

Strong way to verify geometry/exports without a human: drive the running dev app via the Playwright MCP tools and `import()` the model/export modules in-page (init CSG first), then assert watertightness (0 open / 0 non-manifold edges), STL size (`84+tris*50`), and 3MF object counts. This is how every geometry change in this repo has been checked.

**Reload the page between cases in a long sweep.** `csg.ts` never `.delete()`s its Manifold WASM objects, so every boolean leaks. That's harmless in the app (a rebuild is ~10 booleans) but a sweep doing hundreds exhausts the WASM heap and **Manifold then wedges mid-boolean** — the run hangs with no error, which reads exactly like a geometry bug in whichever case was unlucky. A `page.reload()` + re-`initCSG()` per case costs ~1s and avoids it. (Also: a long harness is easier to run as a node script driving Chrome directly than through the MCP tools, which have their own idle timeout — and don't pipe its output through `tail`, which buffers everything until exit so you can't watch progress.)

## Persistence

Anything that crosses the trust boundary (localStorage, `.json` import, `?d=` share URL) MUST go through `serialize.ts` — `coerceDesign()` (calling `coerceModel`/`coerceBox`/`coerceSkadis`) clamps every field to a safe range and drops bad enums, so untrusted input can never produce an invalid `Design`. Don't `JSON.parse` a design and feed it to `buildBin`/`buildBox`/`buildSkadis` directly.

The persisted unit is a `Design` envelope `{ type, bin, box, skadis, litho, fan }` — every model is always present so toggling object type preserves each one's settings. `coerceDesign` is back-compatible: a legacy bare-`BinModel` or `{ model }` shape coerces to `{ type: 'bin', … }`, and a save predating a model (e.g. no `skadis`/`litho`/`fan`) fills that model from its default. One asymmetry: `encodeShareParam` **strips `litho.image` and `fan.image`** (data URLs that would blow the share URL past practical limits) — share links carry the relief settings only, while localStorage/.json keep the image.

Initial design resolution order (`App.initialState`): share URL `?d=` → autosave slot → `defaultDesign()`. Autosave is debounced (300ms) on every change. Named designs are keyed by case-insensitive name (re-saving overwrites). Bump `SCHEMA_VERSION` in `serialize.ts` if the shape changes incompatibly, and handle the migration in the coerce functions.

## Object types: bin, box, skadis, litho, fan

`Design.type` (an `ObjectType`) selects which object is built/shown/exported. The five are independent code paths sharing only the CSG kernel, the exporters, and — for the two relief types — `relief.ts`:

- **bin** → `buildBin` (`geometry.ts`), one mesh. See the two axes + bin geometry below.
- **box** → `buildBox` (`box.ts`), returns **two** meshes (`box` body + `lid`). `box.ts` is self-contained; don't fold box logic into `geometry.ts`.
- **skadis** → `buildSkadis` (`skadis.ts`), **one** mesh (container + hooks fused), so it exports like the bin. Self-contained.
- **litho** → `buildLitho` (`litho.ts`), **one** mesh. Mostly *not* CSG (a direct heightmap mesh — see "Lithophanes" below).
- **fan** → `buildFan` (`fan.ts`), **N** meshes, one per blade, **plus 2 pivot parts** when `pivotStyle` is `'screw'`. Same heightmap-not-CSG approach as the panel (see "Lithophane fans" below).

`litho` and `fan` are the two types **without STEP export** (the button is hidden for both; their `doExportSTEP` cases are unreachable) — a faceted B-rep of a ~200k-triangle relief would be enormous and useless in CAD.

**Every dispatch on `ObjectType` is an exhaustive `switch` guarded by `assertNever`** (in `serialize.ts`, `App.tsx`, `Viewport.tsx`, and `Sidebar.tsx`'s `renderControls`/`doExportSTL`/`doExport3MF`), and the header tabs come from the `TYPE_TABS` array. `OBJECT_TYPES` in `serialize.ts` is the single source of the type set. So **adding another type is compiler-guided**: extend the `ObjectType` union + `OBJECT_TYPES`, and every site that needs a new branch fails to compile until handled. The rest of the recipe: a model + `default*()` + `*OuterSize()` + builder in its own module, a `coerce*` in `serialize.ts` (threaded into `Design`/`SavedDesign`/`defaultDesign`/`serializeDesign`/`coerceDesign` **and** the `StoredDesign` literal in `storage.ts` + the `onLoad` literal in `SaveMenu.tsx`), export functions in `export.ts`, a `TYPE_TABS` row + `*Controls` in `Sidebar.tsx`. Keep each object's geometry in its own module.

Two of those sites are **not** compiler-guarded, so check them by hand when adding a type: the `StoredDesign`/`onLoad` object literals above (a missing field is a type error, so those are safe), and `Viewport`'s image-decode `prep` chain — a new type needing an async decode must be added there or it will build from a cold cache and throw.

## Box top types (`box.ts`)

`BoxModel.topType` is `'sliding' | 'hinged'`, and hinged boxes further split on `hingeStyle: 'flat' | 'top'`; `buildBox` dispatches to `buildSlidingBox` / `buildHingedBox` / `buildTopHingedBox`. Box dimensions are the **inner cavity** (not outer). All builders return watertight `box` + `lid` meshes, modelled Y-up on Y=0.

- **sliding** — lid rides in grooves cut into the top inner edge of the side walls; back wall closed (stop), front open (insert). Exported as **two separate parts** (3MF = 2 objects; STL = `.zip` of `-box.stl` + `-lid.stl`).
- **hinged / flat** — **print-in-place pin hinge** at the back edge. Modelled/printed **open & flat**: box open-top up, lid flat on the plate behind it, joined by interleaved knuckles + a fused pin. Prints supportless with the pin axis along the bed (never on Z — that cracks). Overlapping lip + snap bead hold it shut. Exported as **one print-in-place assembly**, parts left **interlocked in place, NOT moved apart** (3MF = 2 objects in position; STL = one combined `.stl`).
  - **The lid needs TWO articulations to close** — a single plate-level pivot would sweep the lid straight into the back wall (it has to *wrap around* it; this was a real shipped bug). The flat lid is three sections, hinge edge outward: rigid **riser** (length derived from the closed pose, spans the wall height; folds up ~90° at the pin) → full-width **living hinge** (thin membrane, ~0.5mm / 2–3 layers, left at the *plate* side so it prints with no bridging; bends ~90° around the top back edge) → **panel** (lip + snap bead, lands on the rim). The lip rails run along the panel section only — crossing the living hinge would stiffen it solid. Riser length errs ~0.5mm long: slack just leans the riser; too short physically can't close.
- **hinged / top** — chest-style **snap-on hinge at the top back edge**; single rigid lid, no living hinge. Modelled **assembled/closed** (lid on the rim); the two parts print **separately** (lid top-side down) and one downward press snaps the lid's **C-clip knuckles** over the box's pin and the front-lip **bead into a groove** in the front face (no box ridge — the bead nests in a recess so the closed model has zero interference). Box side: boss columns behind/above the back wall hold a fused pin, anchored by ≥45° gussets so they print supportless. **The axis elevation is load-bearing**: the pin sits `axisLift` above the lid top because the panel's back corners sweep circles about the axis when opening, crossing the boss front plane at (their printed depth below the axis) above it — an axis at panel height makes every pin-support placement collide with the closed panel or its swing. Verify swing changes with the exact-CSG rotation test (rotate the lid mesh about the axis through 0–180°, assert `box ∩ lid` stays empty; **negative** X-rotation is opening). Exported like the sliding box (3MF = 2 objects apart; STL = `.zip` of two; the exporter flips the lid to print orientation).

### Hinge clearances (research-backed; don't reduce blindly)

FDM print-in-place sweet spot is **0.2–0.3mm**. Defaults: pin-to-bore `boreGap` ≈ 0.25mm, knuckle-to-knuckle gap ≈ 0.3mm, odd knuckle count (5) so both ends are box knuckles. Too small fuses the hinge solid (the #1 failure); too large is floppy. The `clearance` field drives these. If you touch hinge geometry, re-verify: knuckles interleave (alternating box/lid bands, no overlap) and the exported STL stays **interlocked** (X-extent ≈ box width, not ≈ box+lid moved apart).

## Box textures (`texture.ts`)

`BoxModel.texture = { top, sides, layerHeight }` — the **lid top** and the **outer walls** are independent `TextureSpec`s (`pattern` none/ridges/knurl/hex/dots, `mode` emboss/deboss, `depth`, `pitch`, ridge `angle`). Geometric patterns built as CSG solids (bars, hex prisms, discs — approach "parametric features", chosen over heightfield slabs for exact edges and ~10× fewer triangles) laid over a flat face and applied with **one boolean per face group** as the last step of each builder. No image/organic patterns — that would be a heightfield generator behind the same `FaceRegion` plumbing if ever wanted.

**The print rules are the design, and they live in `TEXTURE` + `PATTERNS`, enforced by `resolveTexture()` — never only in the UI.** Which rules apply depends on how the face prints, so every region is applied with a `TextureContext`:

- `'top-up'` — the **sliding** lid top (exported on its bottom, so this face prints up). Raised or recessed; heights snap to whole `layerHeight`s because the relief *is* the layer stack. Raised relief stands `depth − clearance` above the box rim (the lid top sits `c` below the wall top).
- `'bed-face'` — **both hinged lids**: the fold-flat lid lies face-down in its print pose (its plate face is the closed lid's outer top), and the snap-on lid is exported top-side down. Nothing can be raised below the plate, so `mode` is **forced to deboss**, depth snaps to whole layers and is capped at `MAX_BED_RECESS` (1mm) / `lidT − MIN_LID_REMAINING`. Recesses are pockets the first layers skip and the layer above bridges: `MAX_SPAN` 5mm widest recess, `MIN_FEATURE` 1mm narrowest plateau, `BORDER` 3mm solid margin, and `MIN_PLATEAU` ≥ 50% of the face left on the plate — the `PATTERNS` duty ratios (ridges 0.35, knurl 0.25, hex 0.65, dots 0.6; knurl needs 4mm pitch, the rest 3) are chosen so `plateauFraction()` satisfies that at every pitch, and `resolveTexture` returns null rather than build something that violates it. Defaults (4.5mm pitch) give ridges a 1.6mm groove and a 2.9mm flat.
- `'wall'` — a vertical outer wall. Any pattern, raised or recessed, ≤ `MAX_WALL_DEPTH` 1mm (a raised bar's underside is an overhang that long); no layer snapping (depth is horizontal).

**Regions** are computed by the builders, not the user, and `faceRegion()` insets every edge by `BORDER` so the margin is enforced in one place. Lid top: sliding = the flat between the tongue chamfers (`|x| < ii`), back-wall face to front edge (the pull is beyond); fold-flat = the panel section only, never the living hinge or riser; snap-on = the panel, whose back inset also clears the knuckle arms. Walls (`wallRegions`): sliding = left/right/front stop at the groove ledge (above it the dovetail leaves ~1.2mm of outer wall a recess would breach), back full height; hinged = all stop below the lip band (`outerH − lipH`) so a raised pattern can't collide with the closing lid, and the **back wall is left plain** (knuckle webs / boss columns / riser). The lid's lip rails are never textured (they flex for the snap). Emboss tools embed `EMBED` 0.2mm into the face, deboss tools protrude 0.2mm past it, so no tool face is ever coplanar with the body.

**Knurl is one solid, not two crossed bar sets.** Two tool shells whose faces are coplanar *and overlapping* (the two bar sets' tops) make Manifold leave coincident-but-distinct vertices at the crossings — the exact edge check passes, the quantized (STL) check reports pinched non-manifold edges. `knurlTool` therefore builds the region slab minus the diamond islands (unclipped, taller than the slab, so every island face crosses the slab transversally). Hex/dots/ridges are disjoint shells and don't have the problem. General rule: shells inside one tool mesh, or separate tools in one boolean, must not share coplanar overlapping faces.

**Verifying a texture change** (in the dev app via Playwright, `initCSG()` first): for every pattern × mode on each lid type, exact **and** quantized edge checks 0/0 on both meshes; texture vertices confined to their region (nothing raised outside `BORDER`, nothing raised above `outerH − lipH − BORDER` on hinged walls, nothing on the back wall above the knuckles); recess floors at exactly `n × layerHeight` with no vertices between floor and face; `box ∩ lid` (`A − (A − B)`) empty for the sliding lid in place, the fold-flat hinge, and the snap-on lid through the 0→−180° swing with sides raised to the max; the fold-flat living hinge untouched; `(A_plain − A_textured)/regionArea ≈ 1 − plateau` on the bed face. Persistence: `coerceBox` round-trips a texture, fills defaults for a pre-texture save, and clamps pitch against the pattern's own `minPitch`.

## Skadis holders (`skadis.ts`)

One fused watertight mesh, modelled Y-up on Y=0 (mouth opening at +Y; **+Z = front**, **−Z = back** where the pegboard sits). Dimensions are the **outer** container. `buildSkadis` pipeline: outer tapered solid → subtract cavity → (open bottom) subtract inner-inset floor → (opening) subtract wall wedge → union back plate + hooks → weld.

- **Taper** — one primitive `taperedExtrude(shape, h, y0, bottomScale, topScale)`: build a bevel-free `ExtrudeGeometry` (clean, correctly-wound caps + walls), then scale each vertex's X/Z by a factor from its Y. A bevel-free extrude has vertices **only** at its two ends, so the factor is exactly `bottomScale`/`topScale` → an exact linear taper. `bottomScale = taper/100`, mouth = 1. (ExtrudeGeometry itself can't taper; don't try.) Weld before any boolean, as always.
- **Opening** (`openingSide` + `openingDeg`) — snip a **pie-slice wedge** (apex on the axis, sampled arc) out of the **wall only**: the cut tool spans the floor top (`floorH`) to just past the mouth, so the floor — or the open-bottom rim shelf — stays whole and the holder still has a bottom under its opening. Bisected by the chosen side's azimuth: `front` = +Z, `right` = +X, `left` = −X (there is no `back` — the mount is there). A side opening is just the front wedge rotated a quarter turn. One uniform rule: a clean arc on round, a V-notch on rect. **The cut must never reach the back plate/hooks** — cut the back wall away and the mount bridges two stubs — so `maxOpeningDeg(side)` keeps `BACK_GUARD_DEG` (30°) of container either side of the back bisector: 300° from the front, 120° from a side (still enough to take a whole wall off a square footprint). That max is enforced in three places: `buildSkadis` clamps, `coerceSkadis` clamps against the *resolved* side, and the Sidebar trims the angle when you switch sides.
- **Open bottom** — subtract the inner outline inset by `supportLip` through the floor, leaving a rim shelf.
- **Mount** — `SKADIS` constants are the real pegboard spec: **40mm** hole pitch, **5×15mm** slots, **5mm** board. Hooks sit on the 40mm grid (columns `floor(width/40)+1`, a 2nd row 40mm down when tall enough). `hookStyle` (`'peg' | 'snap' | 'clip'`, built per-hook by `hookParts`) trades holding strength for simplicity: **peg** = friction peg filling the slot; **snap** = thin peg + a catch that drops behind the solid board below the slot (clearance gap, easy on/off); **clip** = same but a deeper catch snug to the board back (strongest). The back plate embeds into the container back so the union is a solid overlap (a tangent line on round backs wouldn't be manifold-safe).
  - **Critical invariant — the plate must seat flush.** The board is a continuous sheet whose only gaps are the slots, so the board thickness can only be gripped between the plate (front) and a catch behind the *solid* board below the slot — there's nowhere to hook in front of the board except the slot itself. **Nothing may enter the "board channel"** (the z gap between the plate face at `-depth/2` and the board back) except the peg threading the slot; anything else (an earlier 45° print-gusset did this) blocks flush seating. Verify with the exact-intersection test: build a board proxy (slab with the slots cut at the hook positions) and assert `holder ∩ board` (`A − (A − B)`, see [[hinge-overlap-verification]]) is **empty**. The hooks are the part most likely to need a real test-print to tune the fit.

## Lithophanes (`litho.ts`)

One watertight mesh, always **modelled** Y-up standing on Y=0 like a framed picture (width X, image height Y, thickness Z; flat back on z=0, relief toward +Z) because that matches the viewport's convention. Dark = thick (defaults 0.8–3mm), `invert` flips; backlight to reveal the picture.

**`orientation: 'flat' | 'standing'`** decides placement for both preview and export, and it is a real design decision, not a slicer convenience — it swaps which printer axis carries tone and which carries detail:

- **flat** (default) — panel on its back, relief up. Tone is stacked in layers, so it's quantised by layer height (~12 greys over 0.8–3mm at 0.2mm layers, ~23 at 0.1mm); picture-plane detail is limited by extrusion width. Fast (15 layers), no brim, zero overhangs. Buying tone is cheap here — halving the layer height doubles the greys and the part is only 3mm thick. Banding is handled by `dither` (below).
- **standing** — panel on its bottom edge. The slicer varies wall width across the 0.8–3mm wall, so tone is effectively continuous and vertical detail gets the layer height — but it's a ~1000-layer thin upright print that wants a brim, and round panels then rely on the `ROUND_FLAT` chord (whose fixed 3mm leaves a 28mm base and ~66° flank overhang at 70mm diameter — scale it if standing discs matter).

**Dithering (`dither` + `layerHeight`, flat only).** Printed flat, the relief height *is* the layer stack, so tone is quantised by layer height no matter what we model — and a gradient crossing a level boundary prints as a hard contour line. `ditherGrid` fixes it the way newspapers print photographs: quantise each sample to the nearest whole layer, then push the rounding error into its neighbours (Floyd–Steinberg weights over a **serpentine** scan — alternating row direction, or the error marches one way and lays down diagonal streaks). Local averages still track the photo, so the eye and the diffused backlight blend adjacent levels into the in-between tone. Measured on a 140×200 photo panel: mean height drift **0.0011mm** versus the smooth relief, 60 distinct heights instead of 2197.

- It is a **deliberate no-op when standing** — there tone is drawn horizontally by varying wall width, so there are no layer steps to dither away and quantising would only discard resolution.
- Range ends round **inward** (`ceil(min/lh)`, `floor(max/lh)`) so no cell can land thinner than `minThickness`; the carried error is clamped before quantising so a run of clipped cells can't smear unbounded error across the panel. Fewer than 2 printable levels → returns null and the relief stays smooth.
- `heightfieldMesh`'s `zAt` takes `(x, y, i, j)` so the precomputed dithered grid is a direct index lookup rather than being re-derived from world coordinates.
- **Verifying it:** every relief vertex must be a whole multiple of `layerHeight` — but only on the un-trimmed path. The CSG outline trim and the mount-hole cut interpolate z along the cells they slice, so a rounded/round panel legitimately shows a few hundred off-grid vertices, all within ~1 sample of the cut. Check with `cornerRadius: 0` + no hole to assert exactly 0 off-grid, then confirm the off-grid ones on trimmed panels sit at the boundary.
- The preview looks *grainier* with dithering on. That's correct — it renders reflected light on a halftone surface; the print is read in transmission.

The orientation transforms are trivially opposite and each lives at its consumer: `orientLithoForPreview` (in `litho.ts`, Y-up) is a no-op when standing and lies the panel down when flat; `lithoExportGeometry` (in `export.ts`, Z-up) applies the usual `toZUp` when standing and **nothing at all** when flat — the model already has its flat back on z=0 with the relief toward +Z, which *is* print space. Verified: flat exports with the whole back face (27,989 of 28,000mm²) on z=0 and the relief up; standing exports on its 344mm² bottom edge strip. `lithoOuterSize` reports axes matching the chosen placement so the dims readout tracks the preview.

- **Heightmap, not CSG.** The panel is emitted directly as a closed **manifold-by-construction** mesh (`heightfieldMesh`): relief grid front, perimeter walls, and a flat back that is just the boundary ring + one centre fan vertex (the back only needs its boundary to match the walls, which halves the mesh). CSG is used only to trim the outline — round / rounded-rect via `csgIntersect` against an extruded outline prism, with the grid overshooting the outline by a margin so the cut never grazes the grid's own walls coplanar — and to cut the optional hanging hole. A sharp-cornered rect with no hole never touches Manifold at all, so that path gets no free validation: any edit to `heightfieldMesh` must re-run the manifold edge check on it specifically.
- **Async image contract.** Image decode is async but builders are sync, so the grayscale bitmap lives in a single-entry cache keyed by the data URL: `await prepareLithoImage(m)` before `buildLitho(m)` — the same shape as the `initCSG()`/`buildBin` contract. `Viewport` and the Sidebar litho export paths do this; `buildLitho` throws if the cache is cold. Uploads are downscaled to ≤800px JPEG (`imageFileToDataURL`) so the embedded data URL stays ~100–200KB.
- **Image mapping** is `object-fit: cover` (scale to fill, crop overflow — never distort), bilinear-sampled; on upload the rect panel height auto-matches the image aspect so nothing is cropped initially. No image → a uniform mid-thickness plate.
- **Round panels** get a `ROUND_FLAT` (3mm) bottom chord so the disc can stand on the bed, and the image maps against the full-circle bounding box so the crop stays centred on the circle.
- The sample grid is capped (`MAX_CELLS`) and the pitch backs off automatically for large panels, keeping the preview interactive (~150ms plain rect, ~900ms with trim + hole).

Note the heightmap mesh, the dithering, the tone curve and the image cache all live in **`relief.ts`** (shared with the fan) — `litho.ts` keeps only the panel's shape and placement. `relief.ts` is a primitive layer like `csg.ts`: it must stay ignorant of panels and blades.

### Tone: luminance → thickness is NOT linear (`thicknessForLuminance`)

The obvious mapping, `thickness = min + (max−min)·(1−luminance)`, is what this did originally and it is **wrong** — it is the main reason a lithophane prints muddy. Light through plastic follows **Beer–Lambert**, transmission = e^(−μt), so a straight thickness ramp does not print as a straight brightness ramp: transmission falls off fastest where the part is thinnest, so a linear ramp spends most of its budget on shadows that are already nearly opaque, crushes the darks together and flattens midtones into highlights. Measured on the 0.8–3.0mm panel range, a requested 50% grey printed at 32% and the mean brightness error across the ramp was **0.16**.

The fix inverts the physics — pick the thickness whose *transmission* lands where the picture wants it, `t(l) = −ln(T(max) + l·(T(min) − T(max)))/μ` — which brings that error to 0 by construction. **Not a free win: it is only correct if μ matches the filament**, which is why `tone` is a dial (a percentage of `TONE_REF_MU` ≈ 1.05 mm⁻¹ for white PLA) rather than a constant, and why the real test is a print. `tone: 0` reproduces the old linear formula *exactly* (verified to 0 drift) — it is both the escape hatch and the μ→0 limit of the same expression, so the small-μ branch is a 0/0 guard, not a separate model. Both object types carry the field and share the one implementation; verify endpoints (l=0 → max, l=1 → min), monotonicity, and that `tone: 0` still equals the linear formula.

## Lithophane fans (`fan.ts`)

**N meshes, one per blade** (like the box's two parts): each blade carries a different slice of the picture, so they are genuinely different parts that happen to share an outline. Built on the same `relief.ts` primitives as the panel — heightmap grid, one `csgIntersect` trim, no final `weld()` (the same pinch-point rule; verify with the **exact index-based** edge test, never a quantized one).

Blades are modelled **blade-local**, Y-up like a panel: pivot at the origin, blade along +Y, thickness +Z with the flat back on z=0. They differ *only* in which part of the photo they sample.

- **The image mapping is the object.** Each blade knows the angle it will sit at in the open fan (`bladeAngle`), so a blade-local sample is rotated into the assembled fan first and the picture read at *that* position — blade 3 carries exactly the slice that lands under blade 3 once opened. The picture is cover-fitted to `fanFrame(m)` (the assembled fan's own XY bbox, deliberately independent of the preview mode) at 100% zoom, then moved by `imageZoom`/`imageOffsetX/Y`. Samples outside the picture return **white** (thinnest), so zooming out gives a clean bright margin instead of the smeared edge pixels an edge-clamp would give. **`imageZoom` MULTIPLIES `mmPerPx`** — 200% makes the picture twice as big on the fan, so the fan sees half as much of it: a tighter crop. Dividing inverts the control, and that was a real shipped bug — at 400% the photo rendered at quarter size and **72% of the relief came out at minimum thickness, i.e. blank**, which reads as a washed-out fan rather than as a framing mistake. Verify with a flat mid-grey image, where any min-thickness cell must be outside the picture: 0.0% blank at 100/200/400%, 32% at 50%. Verified end-to-end with a horizontal black→white ramp: mean blade thickness falls monotonically with the blade's mean X across the fan.
- **The pivot zone must be a flat plate.** Inside `reliefStartRadius(m)` thickness is exactly `hubPlateThickness(m)` (blended out over `HUB_BLEND`), because blades stack and pivot against each other there — relief would make them bind. When dithering, the hub cells are **re-flattened after** `ditherGrid`, or error diffusing in from the relief boundary leaves a layer of speckle on the very faces that have to slide. Verify: every vertex inside the radius is exactly that thickness.
- **`hubPlateThickness` is the blade SPACING, and that makes it load-bearing.** The blades sit eye-to-eye on the barrel, so the eye plate's thickness *is* the gap between blades: blade i occupies z ∈ [i·p, i·p + t], and anywhere two blades overlap (most of the fan) the relief only clears the back of the next blade if `t ≤ p`. The relief reaches `maxThickness`, so the floor is `autoEyeThickness` = `maxThickness + BLADE_SWING_GAP`. Get this wrong and the fan is a solid brick that won't fold — and the dither range and the trim prism height both have to follow the resolved value (the hub-to-relief blend legitimately passes through everything between `maxThickness` and the plate). Verify with `blade_i ∩ blade_{i+1}` over the assembled stack: the only intersection allowed is the **zero-volume coplanar sliver at the eye radius**, which is the eyes touching, i.e. how a stack works.
- **`hubThickness: 0` means auto, and that is a UX fix, not a default tweak.** It used to be only a lower bound with no auto, and the default sat a hair above the floor — so the eye control and the relief control each pinned the other's result. Moving either alone did nothing: dragging the eye across its *entire* range moved the blade 0.1mm, and dropping `maxThickness` moved it not at all while quietly halving the picture's contrast. A thinner blade needed both moved, in the right order, and the app gave no hint of that. **One quantity, one control**: the relief range decides how thick a blade is, the eye tracks it, and `hubThickness > autoEyeThickness` is an explicit "thicker eye for strength" override (a smaller value is floored, so it is a no-op). Saves predating this keep their explicit value and so keep their exact geometry.
- **Contrast is the thickness DIFFERENCE, not the ratio.** This file and the UI both used to say the opposite — "scaling both down keeps the picture" — and that error is what produced a washed-out default. Transmission is e^(−μt), so the lightest:darkest brightness ratio a print can show is e^(μ·(`maxThickness` − `minThickness`)): it is set by how far apart they are, not by `max/min`. Measured against the shipped `thicknessForLuminance`: 0.6–1.8mm and 0.3–0.9mm are both exactly 3× and print at **3.53:1 and 1.88:1** — half the contrast for half the blade. So thinning a blade genuinely costs picture, and that is a real trade against hub stack height, not a free win. It also costs printable grey levels (`greyLevels`), which a finer layer height buys back.
- **The tonal range IS the picture, and the defaults were set by measurement.** 0.35–2.2mm is ~2.8 stops; the 0.6–1.8mm it replaced was 1.8 stops, and a fan built at it looks flat however good the tone curve is. The numbers come from pulling a well-regarded commercial BTS lithophane fan apart (0.33–2.21mm relief, 0.12mm layers, 3 walls, 100% infill, white PLA Basic) — **a thickness map can be recovered from any lithophane 3MF without its source photo**, which is the cheapest way to settle an argument about someone else's tone curve. **The thin end is free**: blade spacing follows `maxThickness` alone (see `hubPlateThickness`), so only the thick end costs stack height — 0.4mm/blade here, ~3.6mm across nine. The fan floor is 0.3mm where the litho panel's is 0.4mm, because a blade always prints flat (a couple of layers) while a panel may print standing, where min thickness is a *wall* and must clear one extrusion width.
- **The default blade proportions are measured, not invented.** Taken off the same commercial fan by rasterising its mesh and reading half-width against distance from the pivot: length:width 4.78, neck:width 0.29, neckLength:length 0.218, 11 blades, eye twice the neck width. Ours match those ratios (4.79 / 0.29 / 0.217 / 11 / 2.00) but at **115mm, not its real 133mm** — at full size the plate layout is 183×283mm and needs two plates, which is what the reference itself ships as; 115mm gives 159×247mm and stays on one 256mm bed. `LAYOUT_MAX_W` only bounds layout *width*, and the viewport's "build plate" is a 600mm reference grid, so **nothing in the app will warn you** if a proportions change pushes the layout off a real bed — check `fanLayout().h` by hand. One thing the ratios do NOT capture: the reference flares over ~83mm from neck to full width, where our derived `flare` does it in ~16mm and then runs parallel. Changing that means changing the formula in `bladeProfile`, which reshapes **every saved fan**, not just new ones.
- **Do not try to nest the blades on the plate.** It looks like free plate width and it is not: the silhouette's full-width body band is long and central, so two blades flipped 180° are *both* at full width over a ~26mm overlap and the required column pitch does not move at all (measured: 24.0mm side-by-side → 24.0mm flipped, at every blade size tried). Flip-plus-axial-shift reaches 19.0mm but only by growing the cell from 107mm to 167mm long, which loses more than it wins. The commercial fan above does not nest either — its columns sit at 29.0mm pitch for a 28.0mm blade, all at the same y.
- **The eye is derived, not a control.** `hubDiameter` = `max(neckWidth, pivotD + 2·HUB_RING)`, so the hole always keeps material around it. Sizing the hole for a printed screw therefore produces the shape a fan blade actually wants on its own — a bulbous eye, a pinched waist, then the flare — rather than that being a styling choice.
- **Blades must overlap — that is what lets a fan fold.** `overlapRadius` computes how far out (adjacent blades Δθ apart overlap wherever `halfWidth(r) > r·sin(Δθ/2)`). It is not a fault to fix: the picture is read in *transmission*, so backlight crosses every blade in the stack and the inner fan always comes out darker than the photo asks. The relief still covers the whole blade by default (`clearOverlap: false`) because **how much is hidden changes as the fan opens** — leave the inner zone blank and it shows as bare plastic the moment someone opens it wider than the modelled spread. `clearOverlap: true` is the opposite aesthetic choice (a deliberately plain inner fan), not a correctness fix. An earlier default of `true` swallowed 69mm of a 100mm blade and threw most of the photo away.
- **The trim tool is built once**, with the pivot hole already subtracted from the prism, so each blade costs **one** boolean instead of two. `effPivotDiameter` caps the hole against the neck width so it always leaves a ring of material.
- **`preview` is preview-only**, unlike the panel's `orientation`: a blade has exactly one sensible print pose. `orientFanForPreview` gives either the fan opened (rotate about the pivot, stack in Z by `maxT + STACK_GAP`, lifted by `-fanFrame().minY` — for a wide spread the outermost blade dips *below* the pivot) or the print layout lain down. `placeFanForPrint` only translates: a blade's modelled pose already *is* print space (back on z=0, relief up), so the exporter rotates nothing. Both preview poses verified sitting exactly on Y=0.
- **`fanLayout`** wraps the row at `LAYOUT_MAX_W` and then evens the rows out, so a full fan still fits a plate. The two pivot parts share one blade cell (a cell is >100mm long, they are ~13mm across), so the grid only grows by one item. Verified no two part footprints overlap.
- **The cell budget is shared across blades** (`MAX_CELLS` total, not per blade), so blade count trades against detail instead of building an unsliceable mesh. It is its own budget, not the panel's: at the panel's 160k split nine ways each blade sampled about a third as densely per mm² as a panel (~0.42mm), which is near one extrusion width so it barely cost picture-plane detail — but it coarsened the **dither halftone**, which is what carries tone between the few layer steps a thin blade has.
- STL is **one combined mesh of the whole plate** (a zip of a dozen near-identical blade files would be useless — they all print together anyway); 3MF is one `<object>` per part in its plate position.

### The pivot screw (`pivotStyle: 'screw'`, `fanPivot`)

A printed **Chicago screw / barrel post**: a flanged post whose barrel threads the blade holes, plus a screw that tightens into the barrel's bore from the far side. `pivotStyle: 'hole'` skips it all and just leaves a hole for an M3 screw.

- **The barrel is a shoulder, and that is the whole point.** Barrel length = stack + `PIVOT_PLAY`, so the screw bottoms against the barrel's end face, never against the blades. Tightening it hard *cannot* seize the fan — which matters, because the object only works if it keeps turning. A plain bolt and nut would clamp the stack solid.
- **The hole has a floor: `MIN_SCREW_PIVOT`.** The barrel must fit through the blade hole (`PIVOT_SLIP`), the bore inside the barrel (`BARREL_WALL`), and the thread in that bore must still be printable (`THREAD.MIN_MAJOR`) — which works out to ~6.8mm. That is why the blade needs a real eye, and why an 8mm hole is the default rather than an M3's 3.2mm. `coerceFan` clamps `pivotDiameter` against the **resolved** `pivotStyle` (the same shape as the skadis opening angle vs. its side), so switching a saved plain-hole design to a screw lands on the smallest hole that can hold a printable thread instead of silently producing a barrel with no thread in it.
- **Only the top of the bore is threaded** (`threadLen ≈ 1.6 × majorD`): the head pulls against the barrel end face right where the engagement is, so a screw as long as the whole barrel would take a dozen turns for no extra strength. The bore may reach down into the flange (leaving a floor), so a two- or three-blade fan still gets what engagement its short barrel allows.
- **Threads print with the axis vertical, so both parts are exported standing while the blades lie flat.** Each turn is then a layer's worth of circle and the ~50° flanks are self-supporting; a thread printed on its side needs supports inside the helix and comes out unusable. Both parts are modelled axis-along-Z in their print pose — which is also the fan's own pivot axis, so the same geometry drops straight into the assembled view.
- **The assembled preview screws it in by phase.** The bore was cut by a tool whose helix is keyed to z=0, so a shaft landing `dz` up the axis only mates when also turned `dz/pitch` of a turn: `orientFanForPreview` applies that `rotateZ`. Without it the modelled screw sits crossing the bore's threads and the assembled fan is interfering solids. (The `rotateX(π)` that flips the screw head-up is a *proper* rotation, so it preserves the thread's handedness — no mirroring involved.)
- **Verifying a thread change — two tests, and the second is the one that matters.** `post ∩ screw` in the assembled pose must be **zero volume** (a few hundred triangles of coplanar sliver where the head rests on the barrel face is contact, not interference). But that passes just as well for a bore that is a plain oversized hole, so also turn the screw **half a pitch out of phase and assert it now collides** (measured: 10.5mm³) — that is what proves the teeth actually interlock rather than the joint pulling straight out.

## Two independent axes: Gridfinity vs sizing

These are separate and must stay separate — a common source of confusion:

- **`gridfinity: boolean`** — whether the bin has Gridfinity *features*: the
  chamfered stacking foot, baseplate clearance, the standard corner radius, and
  magnet/screw sockets. Off = a plain flat-bottomed tray.
- **`customSize: boolean`** — whether the bin is *sized* by unit counts
  (`unitsX/Y/Z` × `gridUnit`) or by freeform mm (`sizeX/Y/Z`).

All four combinations are valid and tested. In `buildBin` the locals are
`gf = m.gridfinity` and `gridded = !m.customSize`. Feet/sockets need `gf`; the
per-cell layout needs `gridded` too (a `gf && customSize` bin gets one foot
spanning the whole footprint instead of per-cell feet). Baseplate clearance is
only subtracted from the footprint when `gf` is on (see `resolvedSize`). The
Sidebar hides the magnet/screw controls when `gridfinity` is off.

## How geometry is built (`buildBin`)

Constructive solid geometry pipeline, in order:

1. Solid rounded-rectangle body (`roundedPrism`) + one chamfered Gridfinity foot per grid cell
2. Subtract the interior cavity → walls + floor
3. Add dividers; subtract finger-scoop cylinders; add label tabs
4. Subtract magnet / screw sockets from the underside
5. Add the stacking lip, then `weld()` the whole thing into one indexed mesh

**Coordinate convention:** Y is up in the viewport; the build plate is at `Y = 0`. Exporters bake a `+90° X` rotation (`toZUp` in `export.ts`) to convert to **Z-up** (slicer convention). (It's +90°, not −90° — −90° prints upside down; that was a real bug we fixed.)

### Hard-won rules for editing geometry — read before touching `buildBin`

- **Additive parts must overlap their neighbours, never touch coplanar.** Coplanar contact in CSG produces open edges. Use the `EPS` overlap constant. Dividers dip into the floor and span past the inner walls; feet overshoot up into the body; the lip overlaps the body top by `EPS`.
- **Tool shells must not share coplanar, overlapping faces** — neither inside one multi-shell tool mesh nor as separate inputs to one boolean. Manifold's coplanar handling then leaves coincident-but-distinct vertices where their side walls cross (exact edge check clean, quantized STL check pinched). Build such features as one solid (see the knurl in `texture.ts`).
- **`ExtrudeGeometry` is not a clean CSG input.** Its caps and walls aren't welded, and Manifold's `ofMesh` rejects non-manifold input. `roundedPrism` runs `weld()` on its output; `toManifold` in `csg.ts` also welds before conversion. Keep both — Manifold throws on bad input rather than silently producing garbage.
- **CSG is async to initialise.** `initCSG()` loads the WASM module once; `App` awaits it and gates rendering/export on a `ready` flag. `buildBin` itself is synchronous and throws if called before init. Don't call `buildBin`/`exportSTL`/`export3MF` before `ready`.
- **CSG is expensive.** The viewport debounces rebuilds (~80ms). Don't move `buildBin` into a render path that runs every frame.

## Watertightness

Output is **guaranteed watertight and manifold** — Manifold operates on manifold meshes and produces meshes where every edge is shared by exactly two triangles. This was switched from `three-bvh-csg` (which left hundreds of non-manifold edges that Bambu Studio rejected) specifically to fix that.

When verifying exports: check structural validity (STL header/size consistency `84 + tris*50`; 3MF is a valid ZIP with the model XML) **and** that the manifold edge check returns 0 open / 0 non-manifold edges. Quantize vertices (~1e-3mm) when checking exported STL because the STLExporter re-expands to non-indexed triangles.

**Exception — the relief types (litho panels and fan blades):** position-quantizing a relief mesh produces FALSE non-manifold edges. Trimming the relief grid leaves a handful of pinch points where two topologically distinct vertices share one position, so quantizing re-does the merge the builders deliberately avoid. Verify litho/fan output with the **exact index-based** edge test on the indexed `BufferGeometry` (which is 0/0), not on quantized STL vertices. Also: when testing any change to either, **use a real image** — `defaultLitho()`/`defaultFan()` have `image: null`, which builds a flat plate and exercises none of the relief/trim topology that actually breaks (this masked a bug once). A regression here means the WASM kernel got bypassed or an input primitive isn't manifold.

Relatedly, when checking that a **dithered** relief sits on the layer grid, "off-grid" is only meaningful for vertices away from *every* cut. The trim interpolates z along each cell it slices, and a fan blade is narrow, so most of it is within a sample of the **side** edges — filter on distance to the local silhouette half-width, not just radially, or a correct mesh looks like it has ~1500 violations. Measured correctly: 24k interior vertices, 0 off-grid, 7 distinct heights.

## Export format notes

- **STL** — binary, via Three's `STLExporter`. File size must equal `84 + triangles*50`; that's the validity check, and it is also a **hard constraint on what an STL may contain**: nothing but the mesh. We once appended the design JSON as a trailing footer on the theory that readers consume `count` triangles and ignore the rest — **they don't**. admesh-derived readers (Bambu Studio, OrcaSlicer, PrusaSlicer) cross-check file size against the header count and, on mismatch, fall back to parsing the file as *ASCII* STL, find no `facet normal`, and reject it with "The file does not contain any geometry data". Design metadata therefore lives only in the 3MF. Never add trailing bytes to an STL. STL has **no concept of separate objects** (one file = one mesh soup), which is why multi-part exports differ from 3MF: a sliding box ships a **`.zip` of two `.stl`s**; a hinged box is one combined `.stl` (single print-in-place assembly); a fan is one combined `.stl` of the whole laid-out plate (a zip of a dozen blades would be worse than useless — they all print together); a bin, a skadis holder and a litho panel are each one `.stl`.
- **3MF** — built by hand: a stored (uncompressed) ZIP of `[Content_Types].xml`, `_rels/.rels`, and `3D/3dmodel.model`. Millimetre units. Supports **multiple objects**: `geometriesToBlob3MF([...])` emits one `<object>` + `<build><item>` per geometry, so boxes export as 2 objects and a fan as one per blade (bins, skadis holders and litho panels as 1). The ZIP writer (string + binary variants) + CRC32 in `export.ts` are intentionally dependency-free; don't pull in JSZip.
- **STEP** — hand-rolled AP214 text writer (`geometriesToBlobSTEP`), dependency-free like the ZIP/3MF writers. A **faceted B-rep**: it can't recover analytic surfaces from a mesh, so every triangle becomes a planar `ADVANCED_FACE`, but with shared `VERTEX_POINT`s and shared `EDGE_CURVE`s (welded position-only via `mergeVertices`, stripping split normals) so the output is a real `MANIFOLD_SOLID_BREP` (one `CLOSED_SHELL`), not triangle soup. Multiple bodies per file (like 3MF): a box exports as 2 solids in **one** `.step` (no zip — STEP holds multiple bodies natively), for both sliding and hinged. Millimetre units. Verify like the others: parse the text and assert Euler `V−E+F==2` per solid, every undirected edge used exactly twice with cancelling orientation (`.T.`/`.F.`), and `ADVANCED_FACE`/`VERTEX_POINT`/`EDGE_CURVE` counts equal the welded topology.
- Models are Y-up; `toZUp()` rotates **+90° about X** to Z-up for export (slicer convention).
- `grep -c "<triangle"` on the 3MF lies — all triangles are on one line, so it returns 1. Count substring occurrences, not lines.

## Conventions

- TypeScript strict mode is on (`noUnusedLocals`, `noUnusedParameters`). The build fails on unused symbols.
- Match the existing comment density — geometry code is heavily commented because the math isn't obvious; UI components are not.
- Keep `GRIDFINITY` constants in `types.ts` as the single source; don't scatter magic numbers into `geometry.ts`.
- Sidebar uses small inline presentational components (`Section`, `Field`, `NumberInput`, `Toggle`, `Seg*`). Reuse them rather than adding bespoke markup.
